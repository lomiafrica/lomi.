lomi. suit un modèle **hébergé d’abord**. Les marchands s’intègrent via notre API cloud, le tableau de bord et le checkout. Nous **ne proposons pas** l’auto-hébergement du traitement des paiements à ce stade.

Notre **direction à long terme** est d’ouvrir progressivement le monorepo, davantage d’apps, davantage de code source, et à terme un chemin supporté pour les opérateurs qui s’auto-hébergent avec leurs propres accords prestataires et leur conformité. Ce n’est pas disponible aujourd’hui ; voir la [feuille de route](#feuille-de-route) pour ce qui est public maintenant.

Nous publions tout de même du code source pour la transparence et les outils d’intégration (SDK, CLI, plugins, docs). Dans cette logique, nous appliquons une **double licence**.

Le projet est principalement sous **GNU Affero General Public License (AGPL)** : la communauté peut utiliser, modifier et redistribuer le logiciel librement. L’AGPL impose toutefois que toute utilisation en service (SaaS notamment) **publie également le code source**. Si vous souhaitez utiliser **lomi.** sans publier vos modifications (intégration à un produit propriétaire) ou l’exploiter commercialement pour des offres similaires, **une licence commerciale est requise**.

Certains composants relèvent exclusivement de notre **licence commerciale**, pour les entreprises ayant besoin de fonctionnalités additionnelles ou d’une plus grande flexibilité. Ce **double modèle** nous permet de servir à la fois la communauté open source et les partenaires enterprise.

## Plateforme hébergée

Pour les paiements en production, utilisez la plateforme sur [lomi.africa](https://lomi.africa/sign-up) : canaux de paiement intégrés, couverture Merchant of Record, mises à jour automatiques et support dédié.

## Feuille de route

Nous ouvrons progressivement le monorepo. **L’auto-hébergement du stack paiement complet est un objectif à long terme**, pas une offre supportée en production aujourd’hui. La trajectoire : publier plus de code → documenter les prérequis opérateur (prestataires, MoR, conformité) → proposer une option auto-hébergée supportée quand le stack sera complet et sûr sans les services hébergés de lomi.

Ce qui est ouvert aujourd’hui :

- **Déjà en open source** :
  - Site de documentation : **`apps/docs`** (ce site)
  - CLI (**`apps/cli`**), outil d’intégration ; s’appuyer sur l’API hébergée, pas sur l’exploitation plateforme
  - Service API : **`apps/api`**
  - SDK : **`apps/sdks`**
  - Plugins e-commerce : dépôts séparés sous `apps/plugins/`, [woo](https://github.com/lomiafrica/woo), [magento](https://github.com/lomiafrica/magento), [prestashop](https://github.com/lomiafrica/prestashop), [shopify](https://github.com/lomiafrica/shopify), [bubble](https://github.com/lomiafrica/bubble)
  - Serveur MCP (**`apps/mcp`**), outil d’intégration ; API marchande dans l’IDE, pas l’exploitation plateforme
  - Plugin agent (**`apps/tools/agent-plugin`**), packaging marketplace pour le MCP hébergé ; [lomiafrica/agent-plugin](https://github.com/lomiafrica/agent-plugin)
  - Boilerplate événements (dépôt séparé) : **[lomiafrica/events](https://github.com/lomiafrica/events/)**

- **Bientôt** :
  - Tableau de bord marchand : **`apps/dashboard`**

- **Propriétaire** :
  - Tableau de bord admin : **`apps/admin`**
  - Application marchande lomi. Pos : **`apps/jumbo`** (`lomiafrica/jumbo`)

- **Produit hébergé (code pas entièrement public)** :
  - Checkout : **`apps/checkout`**
  - Storefront : **`apps/storefront`**
  - Portail client : **`apps/customers`**
  - Site marketing : **`apps/website`**

De nombreux fichiers, surtout les migrations et la logique paiement cœur, portent la mention `/* @proprietary license */` même dans des apps sous AGPL.

## Tableau de bord marchand (`apps/dashboard`)

Le tableau de bord est le back-office marchand (transactions, liens de paiement, paramètres, analytics). C’est un **produit hébergé** aujourd’hui ; le code s’ouvre progressivement.

Structure simplifiée :

```text filename="Tableau de bord (apps/dashboard)"
└── apps/dashboard/
    ├── package.json
    ├── .env.example
    ├── src/              # Application React (Vite)
    ├── supabase/         # Migrations DB et edge functions (référence)
    │   └── migrations/
    └── public/           # Assets statiques
```

Les migrations sous `supabase/migrations/` font foi pour le schéma plateforme. Ce n’est pas une recette pour exploiter votre propre stack paiement sans les services hébergés de lomi. et les accords prestataires.
